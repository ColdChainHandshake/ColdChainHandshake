# Gate 4 review (independent, 28 Nov 2026, HEAD `5054ce2`, branch `rebuild/trust-core`)

**VERDICT: GATE 4 NOT MET.**

The parts that can be proven on a PC agree with each other: the firmware library, the Python generator and the
Kotlin protocol code produce the same bytes. The domain check catches every kind of tampering and truncation
it was tested against. What fails is "detected at handover" in the app. No code path in the app, and no test
above `:core-domain`, ever gives the handover a logger to read. `ServerHandover.loggerLink` is always `{ null }`,
so every handover gets NOT_CHECKED or UNKNOWN. A tampered or truncated logger history has never reached a recorded
verdict, and mutant A1 shows the readings the handover passes to the check are never compared at all. MASTER 5.4
item 2 (the virtual logger in the debug app) and the app half of item 4 (the receiver reads the logger) are not
built; PROGRESS says so itself (line 3: "item 2 … next"; lines 1412 and 1416 unticked). The owner's `HARDWARE = none`
switch waives only "one real reading reaches the receiver's phone", not this.

Method: I read the documents and code listed in the brief, ran the firmware host tests, regenerated the Python
vectors, ran the targeted Kotlin test classes, and ran 19 mutants. I ran no Supabase stack, MCP, Docker, emulator,
device or live test. I used no `local.properties`, keystore or `.env` file. I made one Gradle call at a time,
with targeted classes only.

### Is NOT_CHECKED for every shipment today an honest "met without hardware"?

The design in DECISIONS (28 Nov, line 226) is sound for **server** shipments: a debug virtual logger lives inside
the courier's app, so enrolling it would make every two-phone handover UNKNOWN and prove nothing. It is also an
honest description of the app today. STATUS lines 130-131 say "the virtual logger exists in code but the app
doesn't use it yet".

It is not a reading of "met without hardware". The owner's switch removes one clause: the real reading. "Detected
at handover" stays, and without hardware it can only be shown with the virtual logger. MASTER 5.4 item 2 says
exactly that: "used in tests **and in the debug app**". DECISIONS narrows that to debug local mode, which is a
reasonable narrowing, but that mode is not built (PROGRESS line 3). As it stands, the app's handover path could
lose all of its logger logic without any test noticing. A1 already shows it can lose the readings.

**Gate 4 needs item 2, or at least its testable core.** The minimum to close it:

1. **A test of the handover path with a reachable logger.** In `ServerHandoverTest`, set
   `loggerLink = { virtualLogger }` and give the shipment a non-test key enrolled on the fake server. Then:
   - an honest history records PASS;
   - a reading edited on the server records FAIL;
   - a history cut short of its head records FAIL;
   - a replayed head records FAIL;
   - for each, assert `server.confirmations.last().details.verdict`.

   This would kill A1.
2. **A `HandoverScreenTest` with a FAILED logger.** It should check that the reason line is shown and that
   "Record PASS handover" is absent.
3. **Item 2's debug local wiring, or an owner decision.** Build the debug local wiring as DECISIONS describes it,
   with readings taken from the virtual logger's records and the key taken from the local shipment's record, never
   from the logger. Otherwise the owner records a decision that (1) and (2) are enough for "detected at handover"
   without hardware.
4. **A `VirtualLoggerVectorsTest`.** It closes the PARTIAL in the first row.

## 4. The brief's questions

### Q1. Byte-for-byte agreement on `logger_vectors.json`

**Yes, for the protocol layer.** C++ `Step4Vectors.EveryCharacteristicMatchesThePythonBytes` and the 38 other tests
pass. Python regenerates the file identically. Kotlin's codec and verifier match it (`LoggerVectorsTest`,
`LoggerGattVectorsTest`). **No, for `VirtualLogger` as a logger**, which is untested against the vectors (section 2).
The one key comparison against an outside source is RFC 6979, as STATUS line 112 says.

### Q2. Tampering detected at handover, and does it reach the recorded verdict?

In the domain, yes: `LoggerCheckVerdictTest` (5) and `HandoverOrchestratorTest`'s two logger tests show FAILED and
UNKNOWN lower the verdict and that a declared PASS can't override them. In the app, no logger is ever read (section 2).
Whether Gate 4 needs item 2: **yes, at least its testable core** (section 2, items 1 to 3).

### Q3. The carry-forward rule (an enrolled logger this phone can't reach is UNKNOWN)

**Holds on screen and in the recorded confirmation.**
- Domain: `LoggerHandoverCheck.kt:68-75`, with `LoggerHandoverCheckTest.anEnrolledLoggerThisPhoneCannotReachIsUnknownAndSaysSo`. M1 was killed.
- Recorded: `ServerHandoverTest.anEnrolledLoggerThisPhoneCannotReachKeepsTheHandoverFromPassing` asserts UNKNOWN in `server.confirmations` and refuses a declared PASS. A4 was killed.
- Screen: `HandoverScreenTest.aLoggerOnRecordThatThisPhoneCannotReachIsShownAndHoldsTheVerdict`. A5 was killed.

Gaps:
- **A2 survived.** At `ServerHandover.kt:64`, when the enrolment can't be read, the outcome is UNKNOWN. Changing
  it to NOT_CHECKED passes every test. Today the outcome is correct, but nothing guards it. If `getShipment` fails
  while `hydrateHistory` succeeds (two separate requests), a regression here would record a PASS over an enrolled
  logger that was never read.
- **A3 survived.** At `ColdChainRemote.kt:52-59`, a malformed key on record is meant to come back as an empty array.
  Returning `null` instead turns it into "none enrolled", and no test notices. The server's CHECK constraint
  (`0004:12-13`) makes this unreachable today, so it is defence in depth.
- **The screen falls back to NOT_CHECKED before the first check arrives** (`HandoverScreen.kt:778`,
  `ui.loggerCheck ?: NOT_CHECKED`). Until `loadServerView` finishes, the verdict panel can show PASS for an
  enrolled shipment. This affects only the screen, and briefly: the logger outcome arrives in the same state
  update as the members (`HandoverViewModel.kt:388`), and `receiveOnce` recomputes the outcome before recording.
  Low.

### Q4. 4.3

  - Firmware: `Step3DeviceKey.RefusesTheMirroredTestKey…`.
  - I did not re-check STATUS's claim that neither APK contains the private key (line 113); that needs an APK build.

### Q5. Security (details in section 6)

- Parsing is sound.
- `LoggerGatt` checks exact sizes and refuses left-over bytes (`LoggerGatt.kt:148-157`).
- A page's count must equal its bytes (`:112`).
- More records than asked for are refused as they arrive (`BleLoggerLink.kt:63-69`).
- A forged header claiming a huge range is refused without allocating (`recordsRunExactly`, `LoggerLink.kt:34-38`).
- Test key: covered (Q4).
- Nonce: a fresh `SecureRandom` 16 bytes per check (`LoggerHandoverCheck.kt:50`, `eachCheckSendsItsOwnNonce`).
- Replayed heads: caught. Over BLE they are caught as BAD_SIGNATURE, not STALE_HEAD (G4-6).
- **S9 deferral is acceptable** while no board exists (`HARDWARE = none`) and the library has never run on a device.
  It is written down only in DECISIONS (line 221) and `gate5_review.md`, though, not in `firmware/WALKTHROUGH.md`,
  HANDOFF or THREAT_MODEL, the documents someone porting to a board would read (G4-9).

### Q6. Do the documents say no physical logger was used, and do they claim only what the evidence shows?
